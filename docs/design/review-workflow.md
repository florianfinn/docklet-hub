# Unabhängige Agentenreviews

Jeder bereite PR wird automatisch von der Review-Action in .github/workflows/review.yml geprüft. Sie startet bei opened, synchronize, reopened und ready_for_review und unterscheidet nicht, ob ein Mensch oder ein Agent die Änderung geschrieben hat. Der Reviewer kennt die bearbeitende Sitzung nicht; seine Unabhängigkeit folgt aus dem Aufbau statt aus einer Attestation.

Der Workflow nutzt pull_request_target. GitHub führt damit Workflow-Datei und Skripte aus dem Basisbranch aus, sodass ein PR seinen eigenen Review weder abschwächen noch abschalten kann. Der PR-Head liegt in einem zweiten Checkout unter pr/ und wird nur gelesen: Der Reviewer darf lesen, suchen und git diff, log und show in pr/ aufrufen sowie Inline-Kommentare schreiben. Kein Schritt installiert, baut oder startet Code aus dem PR, solange das API-Secret im Job verfügbar ist. Inhalte unter pr/ gelten im Prompt als Daten, nicht als Anweisungen.

Blockierend sind nur Fehler mit konkretem Fehlerszenario, Sicherheitsprobleme, nicht veröffentlichbare Daten, Verstöße gegen AGENTS.md, die keine automatische Prüfung abdeckt, und geändertes Verhalten ohne Test, der am alten Verhalten fallen würde. Der Reviewer liefert ein strukturiertes Ergebnis mit result, summary und blocking. scripts/report-review.mjs aus dem Basisbranch schreibt daraus einen PR-Kommentar und lässt den Job bei fail oder bei fehlendem bzw. widersprüchlichem Ergebnis fallen. Ein kaputter Review öffnet das Tor also nicht.

Entwürfe überspringt der Job; ready_for_review startet ihn dann. Reine Textänderungen nach scripts/change-scope.mjs bestehen ohne Review, weil CI sie vollständig abdeckt. PRs aus Forks erhalten keine Secrets und lassen den Job ausdrücklich fallen, denn ein übersprungener Pflicht-Check gilt bei GitHub als bestanden. Solche Beiträge übernimmt ein Maintainer in einen Branch dieses Repos. Laufende Reviews eines PRs werden beim nächsten Push abgebrochen.

Das Ruleset für main verlangt PR sowie die Prüfungen checks, pr-text und review, aber keine strikte Aktualität zur Basis. Ohne Merge Queue, die GitHub für Repos persönlicher Konten nicht anbietet, würde strikte Aktualität nach jedem Merge Branch-Aktualisierung, CI-Lauf und neuen Review für alle offenen PRs erzwingen. Das Risiko zweier einzeln grüner PRs, die zusammen brechen, trägt der volle CI-Lauf bei jedem Push auf main; ein solcher Fehler wird sofort per Fix oder Revert behoben. Feature-Branches haben kein Ruleset; dort läuft der Review, wird aber nur als Arbeitsregel durchgesetzt.

Die Action authentifiziert sich mit dem Repository-Secret ANTHROPIC_API_KEY und schreibt Kommentare mit dem Workflow-Token. Jeder Lauf verursacht API-Kosten; deshalb sind Entwürfe und Textänderungen ausgenommen.
